# 实验计划

## 一、实验目标

评估在会议后续协作助手中，引入“可查看、可编辑的结构化记忆层”是否能够帮助用户：

- 更准确地理解 AI 当前记住了什么
- 更快发现 AI 的错误记忆
- 更有效修复错误记忆
- 在下游协作任务中做出更高质量的判断和重规划

本实验不把重点放在“总结质量”上，而是聚焦：

**AI 的记忆是否会影响后续协作决策，以及用户是否能够治理这种影响。**

## 二、研究问题

### RQ1：记忆可见性

当用户可以查看 AI 当前的结构化记忆时，是否能建立更准确的系统心智模型，并提高 perceived control？

### RQ2：记忆可编辑性

当 AI 记错会议内容时，用户能否通过直接编辑记忆，比仅通过继续对话或只读查看更高效地修复错误？

### RQ3：下游协作结果

记忆的 inspectability 和 editability 是否会改善下游任务结果，例如：

- 重规划质量
- 风险识别质量
- 决策一致性判断准确率

### RQ4：控制与成本的权衡

当记忆成为可治理对象后，用户获得的控制收益是否足以覆盖新增的交互成本？

## 三、研究假设

- `H1`：可见记忆相较于隐藏记忆，会提升用户的系统理解和控制感
- `H2`：可编辑记忆相较于只读记忆，会提升错误修复成功率
- `H3`：可编辑记忆会显著提升下游协作任务的正确率
- `H4`：可编辑记忆会增加一定交互成本，但能够改善 trust calibration

## 四、实验设计

### 4.1 设计类型

优先采用 `within-subjects` 设计，并对条件顺序进行 counterbalancing。

原因：

- 样本量需求更低
- 每位参与者都能直接体验三种 memory governance 条件
- 更容易观察修复策略差异

### 4.2 实验条件

#### 条件 A：Hidden

- 不显示记忆面板
- 用户只能继续与助手对话
- 助手内部仍然使用自己的记忆

#### 条件 B：Visible-Readonly

- 显示结构化记忆面板
- 用户可以查看记忆条目与来源
- 用户不能直接修改、删除或新增记忆

#### 条件 C：Visible-Editable

- 显示结构化记忆面板
- 用户可以编辑、删除、补充记忆
- 用户可以标记某条记忆为“不确定”

## 五、任务设计原则

本实验不再使用“follow-up email / action list / owner-deadline”作为主任务，而采用更有研究价值的三任务组合：

### 主任务：冲突消解与重规划

在新约束、新冲突出现后，参与者需要借助助手重新安排任务、责任分工和执行顺序。

### 辅任务 1：风险与阻塞分析

参与者需要识别当前计划中的：

- blockers
- top risks
- 未解决问题
- 潜在升级点

### 辅任务 2：决策一致性审计

参与者需要判断某个后续行动提案是否与会议中的原始决定一致。

这种组合比简单纪要任务更强，因为它测的是：

- 记忆如何影响后续判断
- 错误记忆如何扭曲重规划
- 用户如何修复记忆后改善协作结果

## 六、记忆结构设计

### 6.1 记忆 schema

第一版实验仅保留六类结构化记忆：

- `task`
- `owner`
- `deadline`
- `dependency`
- `constraint`
- `open_issue`

### 6.2 记忆模块的总体设计思路

本实验不采用“单层摘要面板”或“后台黑箱记忆”的设计，而采用**记忆治理式架构**。

核心思路是把记忆模块设计成一个用户可审查、可修复、可追踪的中间层，而不是只在后台供模型调用。

### 6.3 三层核心结构

#### Active Memory

当前真正参与下游任务生成与判断的生效记忆。

#### Proposed Updates

AI 从 transcript、新增冲突或用户后续输入中提取出的候选更新。  
这些更新在用户确认前不应自动进入 Active Memory。

#### Memory Log / Provenance

用于记录：

- 该记忆来自哪里
- 是谁创建或修改的
- 是否曾出现冲突
- 最近一次何时被更新

### 6.4 设计原则

#### 原则 1：Active 与 Proposed 分离

下游任务只应使用 Active Memory。  
AI 新抽取出的候选更新先进入 Proposed Updates，再经过冲突检测和用户审核。

#### 原则 2：每条记忆都应有证据

用户应能查看 transcript 中的来源片段，以便核对系统依据。

#### 原则 3：开放问题必须显式表示

`open_issue` 不应被系统自动折叠成确定事实。

#### 原则 4：系统应暴露冲突，而不是隐藏冲突

当新候选更新与现有 Active Memory 冲突时，应进入 Conflict Queue，供用户处理。

#### 原则 5：系统应暴露记忆对输出的影响

用户不仅应看到“系统记住了什么”，还应看到某次回答、风险分析或重规划实际使用了哪些记忆。

### 6.5 建议字段

每条记忆至少包含：

- `id`
- `type`
- `content`
- `owner`
- `deadline`
- `status`
- `source_ref`
- `confidence`
- `created_by`
- `updated_by`

推荐补充字段：

- `origin`
- `version`
- `active`
- `conflict_state`
- `used_in_last_response`
- `updated_at`

### 6.6 推荐交互能力

对 Visible-Editable 条件，建议支持以下操作：

- 查看记忆
- 编辑字段
- 删除记忆
- 新增记忆
- 接受候选更新
- 拒绝候选更新
- 标记某条记忆为“不确定”

### 6.7 条件映射

#### Hidden

- 不展示 Active Memory
- 不展示 Proposed Updates
- 不展示 Conflict Queue
- 不展示 Source Evidence
- 不展示 Usage Trace

#### Visible-Readonly

- 展示 Active Memory
- 展示 Proposed Updates
- 展示 Conflict Queue
- 展示 Source Evidence
- 展示 Usage Trace
- 但不允许任何直接修改

#### Visible-Editable

- 展示 Active Memory
- 展示 Proposed Updates
- 展示 Conflict Queue
- 展示 Source Evidence
- 展示 Usage Trace
- 允许直接治理记忆

## 七、错误类型设计

第一版只研究可解释、可评分的错误类型：

- `owner_error`
- `deadline_error`
- `constraint_omission`
- `dependency_error`
- `decision_drift`
- `open_issue_as_decided`

## 八、完整实验场景

当前固定 3 个主要场景，每个场景都要包含：

- transcript
- gold memory
- 注入或诱发的错误记忆
- 三个后续任务
- gold scoring rubric

## 场景 1：产品发布协调

### 8.1.1 场景背景

一个跨部门团队讨论新功能发布：

- 市场团队负责对外公告文案
- 工程团队负责最终修复
- 法务团队需要审核对外措辞
- 发布日期初步定在下周四
- 若关键 bug 未修复，则需要顺延

### 8.1.2 关键 gold 记忆

- `task`：市场准备公告文案
- `owner`：市场负责人负责公告文案
- `task`：工程完成修复与回归测试
- `owner`：工程负责人负责修复落地
- `deadline`：发布时间暂定下周四
- `dependency`：公告发布依赖法务审核通过
- `constraint`：若关键 bug 未关闭，则不能发布
- `open_issue`：法务审核时长是否会影响发布时间

### 8.1.3 注入错误

建议注入 2-3 个：

- 把公告文案 owner 记成产品经理
- 漏掉“法务审核后才能发布”
- 把 `open_issue` 错记成“法务已经确认不影响发布时间”

### 8.1.4 新冲突

实验中段加入：

- 法务反馈需要额外 2 天审核
- 核心 bug 尚未完全关闭

### 8.1.5 下游任务

#### 主任务：重规划

让助手重新安排发布时间、责任分工和依赖顺序。

#### 辅任务 1：风险分析

要求助手列出当前 top risks 和 blockers。

#### 辅任务 2：一致性审计

提问：

- 现在能不能对外发公告？
- 本周上线是否还符合会议决定？

### 8.1.6 评分重点

- 是否识别法务依赖
- 是否保留 bug closure constraint
- 是否正确延后发布时间
- 是否避免把未决问题误当已决定

## 场景 2：研究项目推进

### 8.2.1 场景背景

一个研究团队讨论实验推进计划：

- 学生负责起草实验材料
- PI 负责最终审批
- 数据采集必须在伦理批准后开始
- 目标是在两周后启动 pilot
- 招募渠道和预算还未完全确定

### 8.2.2 关键 gold 记忆

- `task`：学生起草实验材料
- `owner`：研究助理负责初稿
- `task`：PI 审核实验材料
- `dependency`：数据采集依赖伦理批准
- `deadline`：两周后启动 pilot
- `constraint`：未获伦理批准不得招募受试者
- `open_issue`：招募渠道尚未确定
- `open_issue`：受试者预算仍待确认

### 8.2.3 注入错误

- 把“研究助理起草材料”记成 PI 负责
- 把 pilot 启动时间提前一周
- 把“招募渠道未定”误写成“使用课程群招募已确认”

### 8.2.4 新冲突

实验中段加入：

- 伦理审批预计会延后 1 周
- 预算审批尚未通过

### 8.2.5 下游任务

#### 主任务：重规划

根据伦理审批和预算延迟，重新安排 pilot 时间、准备顺序和 owner 分工。

#### 辅任务 1：风险分析

输出当前最关键的执行风险和阻塞点。

#### 辅任务 2：一致性审计

提问：

- 现在是否可以开始招募？
- 下周就开始 pilot 是否符合原会议决定？

### 8.2.6 评分重点

- 是否保留 ethics dependency
- 是否区分“未决”与“已决定”
- 是否正确重排启动时间
- 是否识别预算与招募是 blocker

## 场景 3：线上故障修复协调

### 8.3.1 场景背景

一个跨职能团队讨论线上故障修复：

- 工程团队负责 hotfix
- QA 负责验证
- 产品团队负责用户沟通策略
- 只有 QA 确认后才能恢复全部流量
- 对受影响用户的公告措辞必须先过产品审核

### 8.3.2 关键 gold 记忆

- `task`：工程团队完成 hotfix
- `owner`：后端工程负责人负责 hotfix
- `task`：QA 做回归验证
- `dependency`：恢复流量依赖 QA 验证通过
- `constraint`：对外公告需先经产品审核
- `deadline`：当晚 8 点前完成 hotfix 验证闭环
- `open_issue`：是否需要向所有受影响用户发补偿说明

### 8.3.3 注入错误

- 把 hotfix owner 记成 QA
- 把“恢复流量依赖 QA 验证”漏掉
- 把“是否发补偿说明”错记成“已经决定发”

### 8.3.4 新冲突

实验中段加入：

- QA 发现另一个边界 case 尚未验证
- 产品经理临时要求先准备一版用户公告

### 8.3.5 下游任务

#### 主任务：重规划

重新安排修复、验证、公告与流量恢复的执行顺序。

#### 辅任务 1：风险分析

分析当前阻塞项、对用户影响风险和升级点。

#### 辅任务 2：一致性审计

提问：

- 现在能否恢复全部流量？
- 是否已经决定向所有受影响用户发补偿说明？

### 8.3.6 评分重点

- 是否识别 QA 作为关键依赖
- 是否正确保留公告审核约束
- 是否将 open issue 保持为未决
- 是否能基于新冲突重排顺序

## 九、任务流程

每位参与者在每个条件下完成一个场景。标准流程如下：

1. 阅读实验说明
2. 进入当前条件
3. 阅读 transcript
4. 完成一次简短练习
5. 进入正式任务
6. 处理注入错误与新增冲突
7. 完成三类下游任务
8. 填写简短问卷
9. 进入下一个条件
10. 最后完成整体比较反馈

## 十、可测指标

### 10.1 客观指标

- 错误记忆发现率
- 错误记忆修复成功率
- 重规划正确率
- 依赖保持正确率
- constraint preservation score
- 风险识别正确率
- blocker 识别正确率
- 决策一致性判断正确率
- 完成任务总时间
- 从首次接触错误到修复成功的轮数

### 10.2 主观指标

- perceived control
- trust
- confidence in understanding assistant state
- workload
- usability

### 10.3 质性观察

记录并编码：

- 用户如何寻找错误记忆
- 用户何时查看记忆面板
- 用户如何决定信任或怀疑 AI
- 用户如何使用 edit/delete/add
- 用户对“可编辑记忆”价值的解释

## 十一、评分方案

### 11.1 优先使用规则评分

例如：

- owner 是否与 gold 一致
- deadline 是否与 gold 一致
- dependency 是否正确保留
- constraint 是否被遗漏
- open issue 是否仍然被标记为未决

### 11.2 对高层产物使用 rubric

对于重规划结果、风险分析结果和一致性判断，可为每个场景准备评分 rubric：

- 是否识别关键冲突
- 是否保留核心约束
- 是否给出正确的任务顺序
- 是否错误宣称某事已决定
- 是否遗漏关键 blocker

必要时可补充 blinded expert rating，但第一版优先保证规则可判。

## 十二、日志与研究基础设施

系统必须记录：

- session 创建
- condition 分配
- transcript 浏览行为
- memory panel 打开行为

- 每轮用户输入
- 每轮助手输出
- 各项任务完成时间
- 问卷回答

## 十三、样本与执行

### 13.1 Pilot

- 目标样本：`N=5-8`
- 目标：检查任务理解、错误显著性、UI 可用性、评分可行性

### 13.2 Main Study

- 初步目标样本：`N=24-30`
- 采用 within-subject 设计
- 使用 counterbalanced order

## 十四、分析计划

### 14.1 定量分析

- repeated-measures ANOVA 或 mixed-effects model
- 条件间 pairwise comparison
- effect size 报告

重点比较：

- `Hidden` vs `Visible-Readonly`
- `Visible-Readonly` vs `Visible-Editable`
- `Hidden` vs `Visible-Editable`

### 14.2 定性分析

对用户修复策略、信任行为、错误定位方式做 thematic coding。

## 十五、原型实现范围

第一版原型只支持实验所需功能：

- transcript viewer
- 结构化 memory panel
- 条件切换
- 编辑/删除/新增/标记不确定
- 三类下游任务
- 日志记录
- 问卷提交
- 管理端导出

第一版不做：

- 音频转写
- 真邮件发送
- 真项目管理工具集成
- 自动执行 agent action
- 多用户实时协同

## 十七、当前开放问题

- editable 条件是否允许自由文本改写，还是只允许字段级编辑
- 是否在 visible 条件中统一展示 confidence
- 是否在第一版引入“标记 uncertain”
- 每个场景是否只做一轮冲突，还是两轮递进冲突

## 十八、当前建议

第一篇论文建议坚持以下原则：

- 用会议后续协作做主场景
- 把重规划作为主任务
- 把风险分析和一致性审计作为辅助任务
- 保持 schema 精简
- 尽量使用结构化交互和规则评分
- 把主线始终锁定在 memory governance，而不是一般会议总结
